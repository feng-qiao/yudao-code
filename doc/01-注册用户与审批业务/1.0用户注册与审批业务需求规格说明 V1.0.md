# 本草基因组学团队实验室管理平台

## 用户注册与审批业务需求规格说明 V1.0

### 1. 建设目标

建立独立的用户注册申请与审批功能，实现：

1. 申请人在线提交入组或入职申请。
2. 注册审批员审核申请，填写通过或驳回意见。
3. 申请通过后，系统创建正式用户账号并自动授予普通用户角色。
4. 申请未通过或尚未审批时，不允许申请人登录正式系统。
5. 申请人被驳回后，可以修改资料并重新提交，保留完整申请历史。
6. 注册审批权限、普通用户权限、实验室管理员权限和超级管理员权限严格隔离。
7. 全流程保留操作记录，支持追踪申请人、审批人、审批时间和审批结果。

### 2. 技术方案

采用方案 A：独立注册申请表 + 专用审批接口。

不依赖 BPM 工作流引擎，不修改现有质粒审批流程，不把注册审批和质粒审批合并。

注册申请数据与正式用户数据分离。申请提交时不直接创建可登录的正式账号；审批通过后，由后端服务在事务中创建用户并分配固定的普通用户角色。

### 3. 注册对象与固定组织

本阶段注册对象为成都中医药大学本草基因组学团队成员。

- 学校/单位：成都中医药大学，由服务端固定。
- 研究团队：本草基因组学团队，按服务端确定的组织规则处理。
- 登录账号：学号或工号。
- 普通申请人不能自行指定 tenant_id、部门 ID、角色 ID、审批状态或账号启用状态。
- 服务端必须根据可信的配置和组织规则确定租户、部门及普通用户角色，不能直接信任浏览器传入的值。

### 4. 注册申请表字段

#### 4.1 必填字段

1. 姓名。
2. 学号或工号。
3. 身份类别。
4. 研究方向。
5. 手机号码。
6. 电子邮箱。
7. 入学或入职开始年月。
8. 入学或聘用结束年月。

#### 4.2 身份类别

- 硕士
- 博士
- 博士后
- 科研助理
- 教师

#### 4.3 导师与指导教师

- 硕士、博士、博士后：导师和指导教师均为必填。
- 科研助理、教师：导师和指导教师可选。
- 后端必须根据身份类别执行必填校验，不能只依赖前端表单校验。

#### 4.4 研究方向

1. 张三印：中药新药开发与转化平台
2. 黄胜雄：中药药效物质及合成生物学创制平台
3. 陈伟、彭勇：中医药人工智能平台
4. 张玉军、冷梁：生物信息学与GPCR多组学研究平台
5. 鲁军：药物化学与递送系统开发平台
6. 宋驰：中药活性成分筛选与分子育种平台
7. 丛朝彤：中药受体药理学与靶标发现平台

研究方向应使用服务端定义的合法选项或字典值，不能允许申请人随意提交任意方向名称。

### 5. 申请状态与生命周期

申请状态包括：

- PENDING：待审批。
- REJECTED：已驳回。
- APPROVED：审批通过。

基本流程：

1. 申请人填写并提交注册申请。
2. 服务端校验必填字段、身份规则、学号/工号唯一性及其他业务约束。
3. 提交成功后生成申请记录，状态为 PENDING。
4. 待审批申请不生成可登录的正式用户账号。
5. 注册审批员查看申请详情，执行通过或驳回。
6. 驳回时必须填写驳回原因。
7. 通过时，服务端重新校验申请状态、唯一性及角色配置，在同一事务中创建正式用户、分配普通用户角色、更新申请状态并写入审批记录。
8. 事务失败时不得出现“申请已通过但没有正式账号”或“账号已创建但申请仍为待审批”等不一致状态。
9. 已驳回申请人可以修改资料并重新提交。
10. 重新提交应产生新的申请版本或申请记录，并关联之前的申请，不能覆盖或删除历史审批记录。
11. 同一申请不能被重复审批并重复创建账号；并发审批必须有服务端状态校验及必要的数据库唯一性保护。

### 6. 登录与账号安全

1. 登录账号使用学号或工号。
2. 密码只能由服务端使用项目现有安全机制进行单向哈希存储，不得明文存储。
3. 前端“记住密码”仅作为浏览器侧便利功能，不代表服务端保存明文密码；必须评估当前登录组件的实际实现和安全风险。
4. 待审批、已驳回申请人不能凭申请记录登录。
5. 审批通过后才允许使用正式账号登录。
6. 正式账号的启用状态、密码校验和会话创建仍须经过现有登录安全检查。
7. 不接入第三方登录、短信验证、邮件验证或第三方身份服务。
8. 忘记密码的具体自助流程暂不纳入本次开发；本次应调查现有密码重置能力，并明确由管理员重置的现行路径，不得自行设计未经确认的找回机制。
9. 公开注册入口必须受服务端配置控制。关闭注册后，禁止新申请，但不得因此误伤现有正式用户登录。

### 7. 角色与权限

#### 7.1 普通用户

- 审批通过后自动获得普通用户角色。
- 仅能访问已授权的实验室业务功能。
- 不能审批注册申请。
- 不能管理用户、角色或系统权限。
- 不能访问其他用户的申请草稿或修改他人的申请。

#### 7.2 注册审批员

- 只能访问注册申请审批所需的页面和接口。
- 可以查看待审批申请及审批所需的资料。
- 可以通过或驳回申请，并填写审批意见。
- 只能将申请审批为普通用户，不得在审批过程中指定其他角色。
- 不得因拥有注册审批权限而获得质粒审批、库存管理、用户管理、角色管理或系统权限管理权限。
- 不得通过修改前端请求参数获得额外权限。

#### 7.3 本草基因管理员

- 按单独批准的授权范围管理普通用户及指定的业务角色。
- 可以重置用户密码，但不能读取或指定用户的明文密码。
- 不能授予超级管理员角色。
- 不能通过自行修改请求参数或直接调用接口实现自我提权。
- 不自动获得注册审批权限；如确需兼任，必须单独授予明确的注册审批权限。

#### 7.4 超级管理员

- 负责全局系统管理和相关安全配置。
- 负责配置注册审批员及其授权范围。
- 负责配置注册开关和必要的组织、角色映射。
- 高权限操作必须经过服务端权限检查，并留下可追溯记录。

### 8. 菜单与接口隔离

1. 注册申请页面、审批页面和管理员页面按角色分别显示。
2. 菜单隐藏不能代替后端接口鉴权。
3. 所有申请查询、详情读取、编辑、提交、审批、驳回和重提接口都必须在服务端执行权限检查。
4. 申请人只能访问自己有权查看的申请。
5. 注册审批员只能执行注册审批业务。
6. 普通用户不得调用注册审批接口。
7. 本草基因管理员不得越权授予超级管理员角色。
8. 未明确授权的访问默认拒绝。
9. 注册申请接口必须限制非法状态转换、重复提交及并发重复审批。

### 9. 审批记录与审计

至少记录：

- 申请记录 ID。
- 申请人及申请账号标识。
- 申请状态变更前后值。
- 审批人 ID。
- 审批动作：通过或驳回。
- 审批意见或驳回原因。
- 操作时间。
- 关联的前序申请或重提记录。
- 正式账号创建结果及关联用户 ID（审批通过后）。

申请历史与审批记录不得由普通申请人修改或删除。敏感信息应遵循最小必要原则，不得把密码或其他认证秘密写入审计日志。

### 10. 数据库设计原则

预期使用独立的注册申请表，并按需要设计审批历史记录表；最终表数量以只读调查和设计评审结果为准。

申请表字段候选包括：

- 主键 ID、申请编号。
- 姓名、学号/工号、身份类别。
- 服务端确定的租户与组织信息。
- 导师、指导教师、研究方向。
- 手机号、邮箱、开始年月、结束年月。
- 申请状态、驳回原因。
- 申请人提交时间、最后修改时间。
- 关联前序申请 ID。
- 审批人 ID、审批时间。
- 正式用户 ID（通过后关联）。
- 创建时间、更新时间、逻辑删除或版本控制字段（遵循项目现有规范）。

不得在申请表中保存明文密码。密码是否由申请人在申请阶段设置，还是审批通过后通过独立的安全初始化流程设置，必须结合现有登录能力调查后再冻结；本次不得擅自实现未确定的密码初始化机制。

### 11. 业务边界

本阶段不包括：

- BPM 工作流引擎接入或启用。
- 质粒审批逻辑改造。
- 短信、邮件验证码及第三方登录。
- 未经确认的忘记密码自助流程。
- 未经确认的跨租户注册。
- 自动授予注册审批员、本草基因管理员或超级管理员角色。
- 未经批准的大范围菜单、角色或权限清理。
- 直接删除现有正式用户、租户、角色或菜单数据。

### 12. 验收要求

至少验证以下场景：

1. 合法申请可以提交，状态为待审批。
2. 必填字段缺失时后端拒绝提交。
3. 硕士、博士、博士后未填写导师或指导教师时后端拒绝提交。
4. 研究助理、教师可按规则不填写导师和指导教师。
5. 学号/工号重复时，后端拒绝重复注册。
6. 待审批申请不能登录。
7. 已驳回申请不能登录。
8. 审批通过后只创建一个正式账号，并自动授予普通用户角色。
9. 审批员不能给申请人授予其他角色。
10. 普通用户不能调用审批接口。
11. 申请人不能读取或修改其他人的申请。
12. 驳回必须填写原因，重提后历史记录仍可追溯。
13. 重复点击审批或并发审批不会重复创建账号。
14. 伪造 tenant_id、部门 ID、角色 ID 或审批状态不能改变服务端决策。
15. 关闭公开注册后，新申请被拒绝，但现有正式用户仍能正常登录。
16. 注册审批员不能借此获得质粒审批、库存、用户管理或权限管理权限。
17. 本草基因管理员不能授予超级管理员角色，也不能自我提权。
18. 审批事务失败时，申请状态、正式用户和角色关联不会产生不一致数据。
19. 现有登录、现有正式用户、现有租户管理员及质粒 V1/V2 功能不发生非预期回归。

### 13. 变更控制

本文件为需求冻结候选稿，不代表已经授权实施。

任何新增字段、角色、审批规则、权限范围、数据库表或菜单变更，都必须先列出差异并取得负责人确认。实施前必须完成只读调查、设计评审和实施任务单审批。
