> 版本：V2.0

> 上游文档：00-质粒管理V2.0总设计.md

------

# 一、需求概述

质粒管理 V2.0 用于管理实验室质粒从：

```text
质粒类型
→ 质粒登记
→ 审核
→ 正式归档
→ 库存
→ 借用
→ 归还
→ 逾期
→ 违规
→ 黑名单
→ 审计
```

的完整业务生命周期。

系统不再以简单 CRUD 为核心，而采用“档案 + 审核 + 库存 + 借用 + 归还 + 违规”的业务模式。

------

# 二、系统角色

系统涉及三个角色：

1. 普通用户
2. 库管员
3. 超级管理员

------

# 三、普通用户需求

## 3.1 质粒查询

普通用户可以查询系统公开质粒信息。

支持：

- 质粒编号查询
- 质粒名称查询
- 种类查询
- 抗性查询
- 载体名称查询
- 荧光标签查询
- 质粒类型查询
- 创建者查询

查询结果可以查看公开字段。

------

## 3.2 新建质粒

普通用户可以创建自己的质粒登记。

新建后默认为：

```text
草稿
```

草稿状态可以：

- 编辑
- 保存
- 删除
- 提交审核

------

## 3.3 我的质粒

普通用户可以查看自己创建的质粒。

可以看到：

- 基础信息
- 序列图谱
- 保存形式
- 浓度
- 审核状态
- 审核意见

不能看到敏感库存信息。

------

## 3.4 草稿编辑

只有创建者本人可以编辑自己的草稿。

正式提交审核后：

```text
待审核
```

原则上不能继续修改审核中的核心信息。

------

## 3.5 删除草稿

普通用户只能删除自己的草稿。

已经：

- 提交审核
- 审核通过

的正式业务数据不能通过普通用户的删除操作直接删除。

------

## 3.6 Storage 删除规则

Storage（lab_plasmid_storage）是质粒保存档案，不是动态库存账。

Storage 不提供业务删除能力：

```text
普通用户：不能删除 Storage
库管员：不能删除 Storage
超级管理员：不通过业务接口物理删除 Storage
系统：不提供业务 DELETE
```

Storage 一旦形成，应通过状态、失效或其他生命周期机制保留历史记录，不得通过 DELETE 物理删除保存档案。

------

## 3.7 Inventory / InventoryFlow 删除规则

Storage、Inventory、InventoryFlow 共同构成质粒库存历史链：

```text
Storage       禁止业务 DELETE
Inventory     禁止业务 DELETE
InventoryFlow 禁止业务 DELETE
```

三者的正式数据都必须保留，不得通过业务 DELETE 破坏库存历史；停用、失效、生命周期状态等需求通过独立业务机制实现。

# 十、保存信息

## 10.1 保存形式

支持多选：

```text
甘油菌
冻干
质粒DNA
```

------

## 10.2 浓度

必须填写。

单位：

```text
ng/μL
```

必须进行数值校验。

------

## 10.3 测序/检测报告

测序/检测报告：

> 可选。

如果有报告，可以上传。

没有报告不要求填写原因。

------

## 10.4 原始实际位置

用户登记质粒时，填写该质粒当前实际所在的位置：

- 原始质粒保存位置（冰箱/层/盒/位置）
- 原始甘油菌保存位置（冰箱/层/盒/位置）

用途：提交审核后，库管员根据原始位置现场寻找质粒并核查。

正式存储位置不由用户填写，由库管员审核整理后维护。

原始位置与正式位置都必须保留，不得互相覆盖。

------

## 10.5 初始库存申报

用户登记质粒时，申报自己认为的初始库存数量（initial_quantity_declared，单位 μL）。

该值不是正式库存。

库管员审核时现场核查并确认初始库存（initial_quantity_confirmed）。

审核通过后，当前正式库存（current_quantity）以确认值初始化。

------

# 十一、敏感信息

以下属于业务数据，但属于受限数据：

- 质粒体积
- 甘油菌规格
- 甘油菌量
- 质粒存放位置（原始位置 + 正式位置）
- 甘油菌存放位置（原始位置 + 正式位置）
- 初始库存申报值（initial_quantity_declared）
- 初始库存确认值（initial_quantity_confirmed）
- 当前库存（current_quantity）

普通用户不能查看。

库管员只能查看自己负责类型。

超级管理员可以查看全部。


------

# 十七、库存管理需求

库存单位统一：

```text
μL
```

库存包括：

- 当前库存
- 低库存阈值
- 库存状态

库存状态：

```text
可用
低库存
耗尽
停用
```

正式库存业务仅允许对 audit_status = APPROVED 的质粒执行；DRAFT / PENDING / REJECTED 质粒禁止正式库存增减。

------

# 十八、库存操作

库存支持：

### 入库

增加库存，产生 INBOUND 流水。

### 出库

减少库存，产生 OUTBOUND 流水。

### 借用

借用审核通过后自动产生库存扣减，产生 OUTBOUND 流水（不得使用 BORROW 流水类型）。

### 归还

归还审核通过后自动增加库存，产生 INBOUND 流水（不得使用 RETURN 流水类型）。

### 盘点 / 调整

实际盘点与系统库存不一致，或管理人员进行库存校正时，由库管员调整，产生 ADJUSTMENT 流水；管理性调整必须填写原因。盘点数量与当前库存完全一致时不产生流水。

### 报废/处置

字典中保留 DISPOSAL 类型；当前 V2.0 正式业务不实现报废处置流程，未来需要时通过新的需求任务设计。

------

# 十九、库存流水

所有库存变化必须产生库存流水。

流水必须记录：

- 质粒
- 操作类型
- 操作数量
- 操作前库存
- 操作后库存
- 操作人
- 操作时间
- 关联业务单据
- 操作原因
- 备注

禁止前端直接修改当前库存。

流水 quantity 统一保存绝对变更量（不保存负数），增减方向由 flow_type 决定；before_quantity 必须等于变更前真实 current_quantity，after_quantity 必须等于变更后真实 current_quantity。

------

# 二十、低库存预警

库管员可以设置低库存阈值。

例如：

```text
库存 > 100 μL
→ 正常

库存 <= 100 μL
→ 低库存

库存 = 0
→ 耗尽
```

B-3 阶段只实现低库存状态计算，不实现通知发送渠道；低库存时是否通知对应库管员及通知方式，未来另行设计。

------

# 二十一、借用申请

普通用户可以提交借用申请。

申请至少包含：

- 质粒
- 申请数量
- 借用原因

系统自动记录：

- 申请人
- 申请时间
- 当前状态

------

# 二十二、借用审核

借用申请提交后进入：

```text
待审核
```

由对应质粒类型库管员审核。

审核通过时：

- 确定实际借用数量
- 确定归还规则
- 确定归还时间
- 产生库存出库（OUTBOUND，不使用 BORROW 流水类型）

审核拒绝时：

- 不产生库存变化
- 记录拒绝原因

------

# 二十三、申请数量与实际数量

必须分别保存：

```text
申请数量
实际批准数量
```

例如：

```text
申请：500 μL
批准：300 μL
```

不能覆盖原申请数量。

------

# 二十四、归还类型

归还类型固定为五种：

```text
1. 质粒+甘油菌
2. 只归还质粒
3. 只归还甘油菌
4. 无须归还
5. 其他
```

选择：

```text
其他
```

时必须填写自定义说明。

------

# 二十五、归还

需要归还时，系统记录：

- 归还截止时间
- 归还类型
- 应归还数量
- 实际归还数量
- 归还要求
- 备注

------

# 二十六、逾期

系统按照归还截止时间判断：

```text
未到期
↓
到期提醒
↓
逾期
↓
违规
```

可以向用户发送提醒。

------

# 二十七、违规

违规业务用于处理：

- 逾期未还
- 未按要求归还
- 其他借用违规

具体违规类型允许后续扩展。

违规记录必须保存：

- 用户
- 借用记录
- 违规类型
- 违规时间
- 违规说明
- 处理结果
- 处理人
- 处理时间

------

# 二十八、黑名单

黑名单用于限制存在严重或持续违规行为的用户。

支持：

- 加入黑名单
- 查看黑名单
- 移除黑名单

必须记录：

- 用户
- 加入原因
- 加入时间
- 操作人
- 移除时间
- 移除人
- 移除原因

------

# 二十九、用户借用权限

普通用户可以申请借用。

但如果用户处于有效黑名单：

> 系统不得允许其正常提交借用申请。

后端必须进行校验。

不能只依靠前端按钮隐藏。

# 三十三、业务状态总览

## 质粒审核

```text
草稿
 ↓
待审核
 ├── 审核通过
 │      ↓
 │    正式档案
 │
 └── 审核驳回
        ↓
      修改
        ↓
      再提交
```

## 借用

```text
申请
 ↓
待审核
 ├── 驳回
 │
 └── 通过
      ↓
   确定实际数量
      ↓
   库存出库
      ↓
   使用
      ↓
   归还/无需归还
```

## 归还

```text
待归还
 ↓
到期提醒
 ↓
归还申请
 ↓
审核
 ├── 通过 → 库存回库
 └── 驳回 → 按业务处理
```

# 三十四、非功能需求

## 34.1 数据一致性

库存相关操作必须保证事务一致性。

例如借用审核通过时：

```text
借用状态更新
+
库存扣减
+
库存流水生成
```

必须作为一个业务事务处理。

------

## 34.2 权限安全

后端必须进行权限校验。

不能仅依赖前端隐藏按钮。

------

## 34.3 数据追溯

关键业务必须可以追溯：

```text
谁
在什么时间
对哪个对象
执行了什么操作
操作前是什么
操作后是什么
```

------

## 34.4 文件安全

上传文件必须使用系统已有文件管理能力。

不得自行实现一套独立文件存储机制。

------

- 普通用户查看库存数量

# 三十七、Task04-B-3A-FIX 库存业务裁决冻结（2026-10-05）

本节为 Task04-B-3A 调查后由项目负责人正式裁决的库存规则，与正文冲突时以本节为准。

## 37.1 适用范围：仅 APPROVED 正式质粒

正式库存业务（INBOUND / OUTBOUND / STOCKTAKE / ADJUSTMENT）只允许对 `audit_status = APPROVED` 的质粒执行。DRAFT / PENDING / REJECTED 一律禁止正式库存增减。B-2 阶段 DRAFT Inventory（current_quantity = 0）属于登记阶段申报/初始化数据，不构成允许日常库存操作的依据。

## 37.2 流水类型

正式业务仅使用三类流水：INBOUND（库存增加，含日常入库与归还审核通过后的增加）、OUTBOUND（库存减少，含日常出库与借用审核通过后的扣减）、ADJUSTMENT（盘点差异与管理性调整）。BORROW / RETURN 保留为历史/兼容字典值，当前 V2.0 正式业务不得使用，代码不得创建 BORROW / RETURN Flow。DISPOSAL 同理保留，V2.0 不实现报废处置业务。

## 37.3 DISABLED

DISABLED 是库存业务停用状态。质粒被业务停用 → Inventory 置 DISABLED，优先级高于 AVAILABLE / LOW / EMPTY，不得再按数量重算。进入 DISABLED 后禁止 INBOUND / OUTBOUND / STOCKTAKE / ADJUSTMENT。V2.0 暂不实现 DISABLED 恢复业务；未来需要时必须通过新的需求变更任务设计。

## 37.4 删除规则

Storage、Inventory、InventoryFlow 共同构成质粒库存历史链，正式数据不得通过业务 DELETE 删除，三者均不提供业务删除能力。历史数据必须保留；停用、失效等需求通过独立业务机制实现。现有 Inventory / Flow 骨架 DELETE 端点于 B-3 编码阶段移除，本冻结任务不改动 Java。

## 37.5 权限点

统一使用 `lab:plasmid:inventory:query / in / out / stocktake / adjust / flow / threshold / export` 八个权限点；禁止使用 `lab:plasmid-inventory:*`、`lab:plasmid-inventory-flow:*` 作为 V2 正式库存业务权限命名。普通用户库存业务全部禁止；库管员仅可操作自己负责的质粒类型；超级管理员可操作全部。

## 37.6 数量规则

INBOUND：quantity > 0，after = before + quantity。OUTBOUND：quantity > 0 且 before >= quantity，after = before - quantity，库存不足必须拒绝，禁止负库存。ADJUSTMENT：以 actual_quantity 为目标值，adjust_quantity = actual_quantity - current_quantity，after = actual_quantity，且 actual_quantity >= 0。quantity 数据库统一保存绝对变更量（不保存负数），增减方向由 flow_type 决定。

## 37.7 盘点与调整

保留 STOCKTAKE 与 ADJUSTMENT 两个业务入口，均产生 flow_type = ADJUSTMENT 的流水；ADJUSTMENT 必须填写 reason。actual_quantity = current_quantity（零差量）时不产生流水、不更新 last_flow_time，可返回“库存无变化”。

## 37.8 事务与并发

Inventory 更新与 InventoryFlow 插入必须处于同一数据库事务：校验质粒/权限/Inventory → 读取 before → 条件更新 Inventory → 校验更新成功 → 计算 inventory_status → 写 InventoryFlow → 更新 last_flow_time → 提交；任一步失败整体回滚。OUTBOUND 必须使用条件更新（`SET current_quantity = current_quantity - quantity WHERE plasmid_id = ? AND current_quantity >= quantity`）并检查 affectedRows == 1，否则按库存不足/并发失败处理且不写流水。INBOUND / ADJUSTMENT 同样必须保证 before / after / current_quantity / Flow 一致。

## 37.9 阈值与低库存通知

阈值由库管员、超级管理员按权限维护；普通用户禁止修改。修改阈值不属于库存数量变化，不产生 InventoryFlow，但修改后必须重新计算 inventory_status。B-3 只实现低库存状态计算，不实现任何通知发送渠道。

## 37.10 B-2 / B-3 边界

B-2：登记阶段 Storage/Inventory 登记行、initial_quantity_confirmed 确认、current_quantity 初始化与期初 INBOUND。B-3：日常 INBOUND / OUTBOUND、STOCKTAKE、ADJUSTMENT、阈值、状态维护、InventoryFlow 查询、并发控制与权限控制。借用/归还的具体业务接口由后续任务实现，B-3 仅保证库存核心 Service 可被后续业务在事务内复用。
