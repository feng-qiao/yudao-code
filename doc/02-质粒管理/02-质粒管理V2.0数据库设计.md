# 一、数据库设计目标

V2.0数据库不再采用：

```text
lab_plasmid
    +
lab_plasmid_ext
```

简单扩展的方式。

改为按照业务领域拆分：

```text
质粒类型
    ↓
质粒档案
    ├── 保存/存储信息
    ├── 审核历史
    ├── 当前库存
    │      └── 库存流水
    └── 借用
           └── 归还

用户
    ├── 违规
    └── 黑名单
```

设计原则：

1. 一个业务对象一个明确职责。
2. 动态库存独立于质粒基础档案。
3. 库存变化必须保留流水。
4. 审核必须保留历史。
5. 借用与归还独立管理。
6. 违规与黑名单独立管理。
7. 审核状态与库存状态分离。
8. 优先复用 RuoYi-Vue-Pro 框架字段和能力。
9. 不删除现有数据表，先完成V2.0迁移设计。
10. 不允许AI自行修改本数据库设计。

# 六、删除/废弃字段

原 `lab_plasmid` 中：

```text
build_date
type_remark
status
```

不再按原含义使用。

其中：

### `build_date`

当前V2.0需求没有明确要求独立的“构建日期”。

因此暂不纳入核心字段。

### `type_remark`

明确删除。

### `status`

明确废弃原：

```text
0 可用
1 低库存
2 耗尽
3 停用
```

改为：

```text
audit_status
```

以及库存表中的：

```text
inventory_status
```

# 九、audit_status

推荐：

```text
DRAFT
PENDING
APPROVED
REJECTED
DISABLED
```

含义：

| 值         | 含义     |
| ---------- | -------- |
| `DRAFT`    | 草稿     |
| `PENDING`  | 待审核   |
| `APPROVED` | 审核通过 |
| `REJECTED` | 审核驳回 |
| `DISABLED` | 停用     |

数据库可以使用 `varchar(30)`。

这样未来增加状态时比 tinyint 更容易维护和阅读。

最终编码规范以项目既有字典/枚举风格为准。

## 10.3 原始位置与正式位置

Storage 中位置字段分为两类，业务含义不同，不得混写。

### 原始位置（original_*）

```text
original_plasmid_fridge
original_plasmid_layer
original_plasmid_box
original_plasmid_position

original_glycerin_fridge
original_glycerin_layer
original_glycerin_box
original_glycerin_position
```

业务含义：

> 用户登记质粒时，该质粒当前实际所在的位置。

用途：

```text
用户登记
 ↓
填写原始实际位置
 ↓
PENDING
 ↓
库管员根据原始位置现场寻找质粒
 ↓
核查
```

可见性：

```text
普通用户：不可见（不返回）
库管员：可见
超级管理员：可见
```

### 正式位置（plasmid_* / glycerin_*）

```text
plasmid_fridge
plasmid_layer
plasmid_box
plasmid_position

glycerin_fridge
glycerin_layer
glycerin_box
glycerin_position
```

业务含义：

> 库管员审核/整理后的正式存储位置。

可见性：

```text
普通用户：不可见（不返回）
库管员：可见
超级管理员：可见
```

两类位置必须同时保存，禁止用原始位置覆盖正式位置，也禁止审核后丢失原始位置。

例如：

```text
original_plasmid_fridge = F01 / original_plasmid_position = P08
        ↓ 库管员现场核查并整理
plasmid_fridge = F03 / plasmid_position = P15
```

## 10.4 Storage 生命周期与删除规则

Storage 是**质粒保存档案**，不是动态库存账。

```text
DRAFT：用户登记质粒时同步登记 Storage 信息（含原始位置）
PENDING：普通用户锁定；库管员核查时可修正 Storage
APPROVED：Storage 必须存在且唯一
REJECTED：本人修改登记信息（含 Storage 登记信息）后可重新提交
```

删除规则：

```text
普通用户：不能删除 Storage
库管员：不能删除 Storage
系统：不提供业务 DELETE
```

Storage 作为保存档案，通过业务变更保留历史，不做业务删除。

# 十四、动态库存与volume

`lab_plasmid_storage.volume`可以作为：

> 质粒档案/保存信息中的业务静态或辅助信息。

但是：

> **不能作为动态库存唯一来源。**

动态库存必须使用：

```text
lab_plasmid_inventory.current_quantity
```

以及：

```text

```

进行管理。

这是V2.0数据库最重要的边界之一。

## 17.3 三个数量字段的业务语义

`lab_plasmid_inventory` 中三个数量字段不是同义字段，必须严格区分：

### 1. initial_quantity_declared

> 登记人申报的初始库存数量。

用户在 DRAFT 阶段填写，表示用户认为自己当前有多少库存。

**不是正式库存。**

### 2. initial_quantity_confirmed

> 库管员审核时现场核查并确认的初始库存数量。

例如：

```text
用户申报：100.00 μL
现场核查：82.00 μL

initial_quantity_declared = 100.00
initial_quantity_confirmed = 82.00
```

### 3. current_quantity

> 当前正式库存数量（动态库存唯一来源）。

新质粒 APPROVED 正式入库时：

```text
current_quantity = initial_quantity_confirmed
```

**禁止**直接使用 `initial_quantity_declared` 初始化 `current_quantity`。

### 正确流程

```text
DRAFT
 ↓ 用户填写初始库存申报值
initial_quantity_declared
 ↓ SUBMIT
PENDING
 ↓ 库管员现场核查
initial_quantity_confirmed
 ↓ APPROVED
current_quantity 初始化（= initial_quantity_confirmed）
```

### 新质粒与已有正式质粒

- **新质粒**：不存在正式 Storage / Inventory 时，可在正式入库过程中同时初始化 Storage + Inventory。
- **已有正式质粒**：Storage / Inventory 已存在时，**不重复创建**，库管员直接维护现有库存。

### APPROVED 强约束

```text
APPROVED
    ↓
Storage 必须存在且唯一（uk_storage_tenant_plasmid）
+
Inventory 必须存在且唯一（uk_inventory_tenant_plasmid）
```

即：

```text
1 个正式质粒
    ├── 1 条 Storage
    └── 1 条 Inventory
```

# 十九、inventory_status

推荐：

```text
AVAILABLE
LOW
EMPTY
DISABLED
```

含义：

| 状态      | 条件                         |
| --------- | ---------------------------- |
| AVAILABLE | 库存正常                     |
| LOW       | 当前库存 <= 低库存阈值且 > 0 |
| EMPTY     | 当前库存 = 0                 |
| DISABLED  | 库存业务停用                 |

库存状态由后端根据业务规则计算。

前端不能自行决定。

计算优先级冻结为：

```text
if 质粒业务停用 → DISABLED
else if current_quantity = 0 → EMPTY
else if 阈值存在 and current_quantity <= 阈值 → LOW
else → AVAILABLE
```

DISABLED 为人工停用状态，优先级最高，不得仅通过 current_quantity 覆盖。EMPTY 的中文业务含义是“耗尽”，数据库枚举值保持 EMPTY，禁止新增 EXHAUSTED。

# 二十一、库存流水类型

字典 `lab_plasmid_inventory_flow_type` 共含 6 个值：

```text
INBOUND       入库
OUTBOUND      出库
BORROW        借用（历史/兼容值）
RETURN        归还（历史/兼容值）
ADJUSTMENT    盘点调整
DISPOSAL      报废/处置（历史/兼容值）
```

当前 V2.0 正式业务只使用 INBOUND / OUTBOUND / ADJUSTMENT 三类：

```text
日常入库       → INBOUND
归还审核通过    → INBOUND
日常出库       → OUTBOUND
借用审核通过    → OUTBOUND
盘点差异       → ADJUSTMENT
管理性库存调整  → ADJUSTMENT
```

BORROW / RETURN / DISPOSAL 在字典中保留，但正式业务不得使用，代码不得创建相应 Flow。

------

# 二十二、库存流水数量规则

为了避免正负号混乱：

建议：

```text
quantity
```

统一保存：

> 本次业务实际变化量的绝对值。

通过：

```text
flow_type
```

判断增加或减少。

例如：

```text
入库（INBOUND）100
借用扣减（OUTBOUND）20
归还增加（INBOUND）10
盘点调整（ADJUSTMENT）5
```

而不是：

```text
+100
-20
+10
-5
```

最终计算由业务类型决定。

这样更容易避免前端传入错误的负数。

# 二十三、库存事务要求

库存变化必须：

```text
校验质粒（APPROVED 且未停用）
↓
校验权限
↓
锁定库存记录
↓
读取当前库存（before_quantity）
↓
计算新库存（after_quantity）
↓
条件更新库存
↓
校验更新成功
↓
计算 inventory_status
↓
写入库存流水
↓
更新 last_flow_time
↓
提交事务
```

必须避免并发情况下：

```text
库存被重复扣减
```

后端需要使用事务和适当的行锁/乐观并发控制。OUTBOUND 必须使用条件更新：

```sql
UPDATE lab_plasmid_inventory
SET current_quantity = current_quantity - #{quantity}
WHERE plasmid_id = #{plasmidId}
  AND current_quantity >= #{quantity};
```

并检查 affectedRows == 1；affectedRows == 0 时按库存不足/并发失败处理，不得写入流水。INBOUND / ADJUSTMENT 同样必须保证 before / after / current_quantity / Flow 一致。

盘点或调整为零差量时不产生流水、不更新 last_flow_time。

具体实现方式由后端按照项目规范确定。

# 三十六、为什么 storage 独立

`lab_plasmid`保存：

> “这个质粒是什么”。

`lab_plasmid_storage`保存：

> “这个质粒怎么保存”。

这样可以避免基础档案表越来越臃肿。

------

# 三十七、为什么 audit 独立

审核是历史过程。

例如：

```text
第一次提交 → 驳回
第二次提交 → 驳回
第三次提交 → 通过
```

如果只在 `lab_plasmid` 中保存：

```text
audit_status
reviewer
review_time
```

历史会被覆盖。

所以必须：

```text
lab_plasmid
+
lab_plasmid_audit
```

------

# 三十八、为什么 inventory 独立

库存是动态变化数据。

如果直接：

```text
lab_plasmid.volume = 800
```

无法回答：

```text
为什么变成800？
谁扣的？
什么时候扣的？
扣了多少？
因为哪次借用？
```

因此：

```text
inventory
+
inventory_flow
```

必须分离。

------

# 三十九、为什么 borrow 和 return 独立

借用和归还是两个不同业务动作。

例如：

```text
借用300
第一次归还100
第二次归还100
第三次归还100
```

所以：

```text
borrow 1:N return
```

比把归还信息全部塞进借用表更加合理。

# 五十五、Task04-B-3A-FIX 库存业务裁决冻结（2026-10-05）

本节为 Task04-B-3A 调查后由项目负责人正式裁决的库存规则，与正文冲突时以本节为准。

## 55.1 适用范围：仅 APPROVED 正式质粒

正式库存业务（INBOUND / OUTBOUND / STOCKTAKE / ADJUSTMENT）只允许对 `audit_status = APPROVED` 的质粒执行。DRAFT / PENDING / REJECTED 一律禁止正式库存增减。B-2 阶段 DRAFT Inventory（current_quantity = 0）属于登记阶段申报/初始化数据，不构成允许日常库存操作的依据。

## 55.2 流水类型

正式业务仅使用三类流水：INBOUND（库存增加，含日常入库与归还审核通过后的增加）、OUTBOUND（库存减少，含日常出库与借用审核通过后的扣减）、ADJUSTMENT（盘点差异与管理性调整）。BORROW / RETURN 保留为历史/兼容字典值，当前 V2.0 正式业务不得使用，代码不得创建 BORROW / RETURN Flow。DISPOSAL 同理保留，V2.0 不实现报废处置业务。

## 55.3 DISABLED

DISABLED 是库存业务停用状态。质粒被业务停用 → Inventory 置 DISABLED，优先级高于 AVAILABLE / LOW / EMPTY，不得再按数量重算。进入 DISABLED 后禁止 INBOUND / OUTBOUND / STOCKTAKE / ADJUSTMENT。V2.0 暂不实现 DISABLED 恢复业务；未来需要时必须通过新的需求变更任务设计。

## 55.4 删除规则

Storage、Inventory、InventoryFlow 共同构成质粒库存历史链，正式数据不得通过业务 DELETE 删除，三者均不提供业务删除能力。历史数据必须保留；停用、失效等需求通过独立业务机制实现。现有 Inventory / Flow 骨架 DELETE 端点于 B-3 编码阶段移除，本冻结任务不改动 Java。

## 55.5 权限点

统一使用 `lab:plasmid:inventory:query / in / out / stocktake / adjust / flow / threshold / export` 八个权限点；禁止使用 `lab:plasmid-inventory:*`、`lab:plasmid-inventory-flow:*` 作为 V2 正式库存业务权限命名。普通用户库存业务全部禁止；库管员仅可操作自己负责的质粒类型；超级管理员可操作全部。

## 55.6 数量规则

INBOUND：quantity > 0，after = before + quantity。OUTBOUND：quantity > 0 且 before >= quantity，after = before - quantity，库存不足必须拒绝，禁止负库存。ADJUSTMENT：以 actual_quantity 为目标值，adjust_quantity = actual_quantity - current_quantity，after = actual_quantity，且 actual_quantity >= 0。quantity 数据库统一保存绝对变更量（不保存负数），增减方向由 flow_type 决定。

## 55.7 盘点与调整

保留 STOCKTAKE 与 ADJUSTMENT 两个业务入口，均产生 flow_type = ADJUSTMENT 的流水；ADJUSTMENT 必须填写 reason。actual_quantity = current_quantity（零差量）时不产生流水、不更新 last_flow_time，可返回“库存无变化”。

## 55.8 事务与并发

Inventory 更新与 InventoryFlow 插入必须处于同一数据库事务：校验质粒/权限/Inventory → 读取 before → 条件更新 Inventory → 校验更新成功 → 计算 inventory_status → 写 InventoryFlow → 更新 last_flow_time → 提交；任一步失败整体回滚。OUTBOUND 必须使用条件更新（`SET current_quantity = current_quantity - quantity WHERE plasmid_id = ? AND current_quantity >= quantity`）并检查 affectedRows == 1，否则按库存不足/并发失败处理且不写流水。INBOUND / ADJUSTMENT 同样必须保证 before / after / current_quantity / Flow 一致。

## 55.9 阈值与低库存通知

阈值由库管员、超级管理员按权限维护；普通用户禁止修改。修改阈值不属于库存数量变化，不产生 InventoryFlow，但修改后必须重新计算 inventory_status。B-3 只实现低库存状态计算，不实现任何通知发送渠道。

## 55.10 B-2 / B-3 边界

B-2：登记阶段 Storage/Inventory 登记行、initial_quantity_confirmed 确认、current_quantity 初始化与期初 INBOUND。B-3：日常 INBOUND / OUTBOUND、STOCKTAKE、ADJUSTMENT、阈值、状态维护、InventoryFlow 查询、并发控制与权限控制。借用/归还的具体业务接口由后续任务实现，B-3 仅保证库存核心 Service 可被后续业务在事务内复用。
