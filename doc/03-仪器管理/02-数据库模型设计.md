# 一、设计目标与原则

## 1.1 目标

1. 为仪器管理建立**独立业务域**的物理表模型，表前缀统一 `lab_instrument_*`。
2. 与 `lab_plasmid_*` 严格隔离，不与质粒业务混表。
3. 覆盖《仪器管理需求 V1.1》全部 20 项逻辑实体，映射为 **20 张物理表**。
4. 支撑 F1~F20 冻结规则（尤其信用账户唯一初始化、预约冲突、冻干批次、工单路由）。

## 1.2 通用规范（沿用 lab 模块实证规范）

| 项 | 规范 | 依据 |
| --- | --- | --- |
| 存储引擎 | `InnoDB` | `20261004_lab_plasmid_v2.sql` |
| 字符集/排序 | `utf8mb4` / `utf8mb4_unicode_ci`（见第七章待确认 G1） | lab 业务表实证 |
| 主键 | `id bigint(20) NOT NULL AUTO_INCREMENT` | 同上 |
| 公共审计字段 | `creator varchar(64)` / `create_time datetime` / `updater varchar(64)` / `update_time datetime` | 同上 |
| 逻辑删除 | `deleted bit(1) NOT NULL DEFAULT b'0'` | 同上 |
| 租户 | `tenant_id bigint(20) NOT NULL DEFAULT 0` | 同上 |
| 外键 | **不建物理外键**，仅逻辑关联 + Service 校验 | lab 全部 DDL 实证 |
| 唯一键范式 | `uk_<语义> (tenant_id, <业务键>)`；`deleted` **不进入**唯一键 | `uk_type_tenant_code` 实证 |
| 建表语句 | 未来 DDL 使用 `CREATE TABLE IF NOT EXISTS`（幂等） | 同上 |
| 状态字段类型 | 统一 `varchar(30)`（可读、可扩展），取值见 00 文档状态机；替代方案见待确认 G2 | 参考 `lab_plasmid.audit_status varchar(30)` |
| 枚举双轨 | 字典给前端展示，Java 枚举给后端判断 | MES `MesDvRepairStatusEnum` 范式 |
| 基类 | 业务 DO 统一继承 `TenantBaseDO` | `RegisterApplyDO` 实证 |

> **说明**：本设计表中"是否允许 NULL"与"默认值"均显式给出；`creator/create_time/updater/update_time/deleted/tenant_id` 六列在每张表均存在，后续各表字段清单不再重复罗列（仅在需要特殊说明时注明）。

# 三、各表字段定义

约定：以下字段清单中，公共字段（`id / creator / create_time / updater / update_time / deleted / tenant_id`）统一为：

```text
id          bigint(20)  NOT NULL AUTO_INCREMENT  PK
creator     varchar(64) NULL DEFAULT ''
create_time datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP
updater     varchar(64) NULL DEFAULT ''
update_time datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
deleted     bit(1)      NOT NULL DEFAULT b'0'
tenant_id   bigint(20)  NOT NULL DEFAULT 0
```

**冲突判定表达式**（左闭右开）：

```sql
-- 请求时段 [reqStart, reqEnd)，设备 deviceId
SELECT COUNT(*) FROM lab_instrument_reservation
WHERE device_id = #{deviceId}
  AND deleted = 0
  AND status IN ('PENDING','FINISHED')       -- 有效预约 + 已实际使用历史（C3：FINISHED 不释放）；IN_USE 未来加入；CANCELED/VOIDED 才排除
  AND start_time < #{reqEnd}
  AND end_time   > #{reqStart};
```

维护时段与冻干批次同理各查一次，合并判定。

**并发保护（三层）**：

| 层 | 手段 | 说明 |
| --- | --- | --- |
| 1 | **事务 + 设备行锁** | 事务内 `SELECT * FROM lab_instrument_device WHERE id=#{deviceId} AND deleted=0 FOR UPDATE`，以设备行为串行化锚点，使同一设备的并发预约请求串行 |
| 2 | 冲突查询 | 锁内执行 4.1 冲突查询，命中即拒绝 |
| 3 | 条件约束 | 落库后（如需）以条件更新/复核保证；设备行锁已足够，无需额外唯一键（时间区间无法用唯一键表达） |
| 4（可选） | `@Idempotent` | 防用户快速重复提交同一预约 |

> **不得只用前端校验**（F6）。锁维度选择"设备行"而非"预约行"，因预约行在插入前不存在。

## 4.2 信用账户初始化（F2，最多一次）

| 层 | 手段 |
| --- | --- |
| 1 | DB 唯一键 `uk_account_tenant_user (tenant_id, user_id)`：并发插入只有一个成功 |
| 2 | Redisson 锁 `instrument:credit:account:{tenantId}:{userId}`：锁内"查不到则插入" |
| 3 | 与资质审核通过**同一事务**：审核通过 → 尝试初始化账户（存在则跳过，**不重复赠送**） |

## 4.3 信用加扣分（并发调整）

| 层 | 手段 |
| --- | --- |
| 1 | 事务内 `SELECT * FROM lab_instrument_credit_account WHERE id=#{id} FOR UPDATE` 锁定账户行 |
| 2 | 读取当前 score → 计算 newScore → 更新 score + 插入流水（同一事务） |
| 3 | 流水不可变（不提供删除/修改接口），保证审计 |

## 4.4 单 ACTIVE 关系（manager / qualification）

参照质粒黑名单范式：Redisson 锁（按 target/user 键）+ 锁内"查询 ACTIVE → 置旧行 RELEASED → 插入新 ACTIVE"。

## 4.5 冻干批次创建

同 4.1：锁设备行 + 锁内冲突查询（仅排除 CANCELED；OPEN/RUNNING/FINISHED 均为实际/计划占用，C3 同口径），命中即拒绝（F7）。

## 4.6 工单分配

分配为"读负责人配置 → 写 handler"，用条件更新 + `affectedRows` 校验防并发重复分配。

# 五、数据隔离方案

| 项 | 方案 |
| --- | --- |
| 多租户隔离 | 全部表含 `tenant_id`，DO 继承 `TenantBaseDO`，MyBatis 租户插件自动追加 `tenant_id` 条件（含手写 SQL 经插件改写） |
| 逻辑删除 | 全部表 `deleted bit(1)`；业务删除一律软删，不做物理 DELETE |
| 唯一键 + 软删 | 唯一键 `(tenant_id, 业务键)` 不含 `deleted`；软删后同业务键不可重插，由 Service 处理（沿用 lab 现状） |
| 数据权限 | 管理端列表用 `@DataPermission` 做部门维度可见范围；**"负责人只管自己负责设备"必须在 Service 层显式校验**（不能只靠数据权限规则，F18） |
| 附件隔离 | `infra_file` 无 `tenant_id`，附件可见性由**业务表归属**控制（如 reservation.device_id / repair_order.reporter_user_id） |
| 跨租户 | 禁止跨租户读取；Job 类任务加 `@TenantJob` 逐租户执行 |
