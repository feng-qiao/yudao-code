# 一、设计目标

1. 建立**一套可被多种仪器复用的预约规则引擎**，不为每台仪器单独写预约逻辑。
2. 把**"预约时间粒度"与"最短预约时长"彻底分开**（F13），避免"最短 6 小时"被误解为"只能预约 6/12/18 小时"。
3. 支持酶标仪**后台可配置开放窗口**（F14），用配置表达未确认的"周三/周日→日期"映射。
4. 支持 BLI **粒度为待确认参数**（F15），未配置时不可预约，绝不采用未确认的默认粒度。
5. 支持细胞膜色谱平台下**多设备、不同规则、设备级负责人**（F16）。
6. 时间冲突由**数据库事务/锁**保证，不依赖前端（F5/F6）。

# 二、规则字段定义与语义

规则实体：`lab_instrument_booking_rule`（每设备 1:1）。字段语义如下：

| 字段 | 语义 | 合法取值 | 为空表示 |
| --- | --- | --- | --- |
| `granularity_minutes` | **时间粒度**：预约边界对齐的最小步长 | 正整数（如 15/30/60） | 未配置 → 不可预约 |
| `min_duration_minutes` | **最短时长**：单次预约的最小持续分钟数 | 正整数（如 360） | 未配置 → 不可预约 |
| `max_duration_minutes` | **最长时长** | 正整数（≥ min） | 为空 = 不限制上限 |
| `bookable_days_before` | 可预约起始偏移（可往前 N 天） | 整数 ≥ 0 | 为空 = 从今天起 |
| `bookable_days_ahead` | 可预约日期范围（往后 N 天） | 整数 ≥ 0 | 为空 = 不限制 |
| `open_days` | 每周开放日 | 逗号分隔 1(周一)~7(周日) | 为空 = 每天开放 |
| `open_start_time` / `open_end_time` | 每日开放时段 | `HH:mm` | 为空 = 全天开放 |
| `allow_admin_adjust_after_start` | 管理员是否可在开始后调整 | bit | — |
| `enabled` | 规则是否启用 | bit | — |

> 关键：`granularity_minutes` 与 `min_duration_minutes` 是**两个独立概念**。规则引擎中：
> "粒度"决定**可选的边界刻度**；"最短时长"决定**单次预约持续时间的下界**。
> 二者组合不产生"只能预约 N 倍最短时长"的限制（F13 明确禁止这种误解）。

# 三、规则优先级（判定顺序）

预约请求在创建时，按**固定顺序**逐项判定，任一不通过即拒绝并返回**明确原因码**：

```text
P1 设备状态      device.status == NORMAL               否则拒绝（MAINTENANCE/FAULT/DISABLED/SCRAPPED）
P2 可预约开关    device.bookable == 1                  否则拒绝
P3 规则已启用    rule.enabled == 1                     否则拒绝（未配置不可预约，F15）
P4 用户资质      qualification(target=**DEVICE**).status == ACTIVE 否则拒绝（第一期仅设备级，C4）
P5 用户暂停      suspend 无生效中的 SINGLE(本设备) / ALL                   否则拒绝（F9）
P6 开放范围      在 bookable_days_before/ahead 内、在 open_days/open_time 内、命中开放窗口（酶标仪）  否则拒绝
P7 时间参数      粒度对齐、[min,max] 时长约束               否则拒绝
P8 时间冲突      reservation/maintenance/freeze_batch 无重叠 否则拒绝（F5）
P9 落库          事务内锁 + 插入                           失败回滚
```

优先级说明：**先权限（P1-P5）后时间（P6-P9）**。权限不通过时不进行时间计算，减少无谓计算与信息泄露。

# 四、预约时间计算方法

## 4.1 时间粒度对齐

请求携带 `requestedStart`、`requestedEnd`（用户可只给起始 + 时长）。系统计算：

```text
1) 校验 granularity_minutes 已配置；
2) 校验 start 对齐粒度（epochMinute % granularity == 0），未对齐则拒绝或由前端吸附；
3) 校验 end 对齐粒度；
4) duration = end - start（分钟）；
5) min_duration_minutes <= duration <= max_duration_minutes（max 可空）。
```

## 4.2 持续时间计算与递增（通用）

```text
duration = end - start
若 duration < min_duration_minutes → 拒绝
若 max_duration_minutes 非空 且 duration > max → 拒绝
递增步长 = granularity_minutes（步进由用户/前端按粒度选择，不强制等于最短时长）
```

> **蛋白纯化仪示例（F13）**：`min_duration_minutes = 360`（6h）。用户可选择 `start=09:00`，`end=15:00`（6h）→ 允许；`end=18:00`（9h，若粒度为 30 分钟则 9h 对齐）→ 允许；**不存在**"只能选 6h/12h"的隐含约束。**但 6h 之后的递增粒度尚未确认（U1）**：设计中 `granularity_minutes` 留空由业务配置，**不得写死**。

## 4.3 跨天与结束时间

- `end` 必须 > `start`。
- 允许跨天（如冻干机不在此列，冻干走批次模型；普通预约是否允许跨天由 `rule` 决定，默认允许由业务配置）。
- 结束时间右开：`[start, end)`，与 OA 会议室预定一致（相邻预约不冲突）。

# 五、预约开放判断方法

## 5.1 通用开放判断（rule 层）

```text
openByDateRange: bookable_days_before/ahead 命中
openByWeekday:   open_days 为空 或 目标日期星期 ∈ open_days
openByTimeOfDay: open_start_time/end_time 为空 或 预约时段落在每日开放时段内
```

## 5.2 酶标仪开放窗口（F14，`booking_window`）

酶标仪在 rule 通用开放之上，叠加**多条窗口配置**：

```text
窗口 = {
  open_days:           每周开放日
  open_start_time/end: 开放时段
  target_date_start/end: 开放目标日期范围
  target_week_mapping: 开放日→目标日期的映射说明（未确认，文本表达）
  capacity / used_count: 剩余预约能力
}
```

判断逻辑：

1. 目标日期落在**任一** ACTIVE 窗口的 `target_date_start~end` 内；
2. 目标日期星期 ∈ 该窗口 `open_days`；
3. 预约时段落在窗口 `open_start_time~end_time`；
4. 若 `capacity` 非空：`used_count < capacity`（剩余能力判断）。

**待确认（U2）**："周三、周日"对应的**具体日期映射**及**开放目标日期范围**未确认。设计中通过 `target_week_mapping` + `target_date_*` **以数据配置表达**，运行时由业务方填写；**不得在设计中将某一固定映射写成业务规则**。

**案例（示意，映射数值待确认）**：

| 窗口 | open_days | open_time | target_date_start~end | capacity | 剩余能力 |
| --- | --- | --- | --- | --- | --- |
| 周三批次 | 3 | 09:00-11:00 | 由业务填写 | N | capacity-used_count |
| 周日批次 | 7 | 14:00-16:00 | 由业务填写 | M | capacity-used_count |

# 六、特殊仪器规则设计

## 6.1 蛋白纯化仪

- `min_duration_minutes = 360`（已确认）。
- `granularity_minutes` **待确认（U1）** → 设计中留空。**若留空则不满足 P3，不可预约**；业务确认后配置启用。
- 明确否决："最短 6 小时"≠"只能预约 6/12/18 小时"。

## 6.2 酶标仪

- 使用 `booking_window` 多窗口模型（5.2）。
- 通用 rule 提供基础粒度/最长时长；窗口叠加"每周开放 + 目标日期段 + 剩余能力"。
- 映射未确认 → 全部通过配置表达（U2）。

## 6.3 BLI

- `granularity_minutes` / `min_duration_minutes` / 最长时长**均待确认（U3）**。
- 设计中对应设备 `rule.enabled = 0`（未配置）→ **不可预约**（P3 拦截）。
- **不得**为 BLI 设置任何默认粒度。

## 6.4 细胞膜色谱平台（F16）

- 平台下**多台设备**（装柱机、色谱设备等），**每台设备独立 rule**（1:1），可有**不同**预约规则。
- 每台设备可有**设备级负责人**（`manager.scope=DEVICE`），负责人只能审核/调整其负责设备。
- 平台级负责人（`scope=PLATFORM`）可覆盖平台内多设备。
- **设备级规则优先于平台级默认**：平台不设统一 rule，全部落在设备。

## 6.5 冻干机

- 不走普通 reservation 时间区间规则，走 `freeze_batch` 批次模型（详见 05）。
- 但**开放判断（P6）与冲突（P8）仍复用本引擎**：批次时段必须同时不与 reservation / maintenance / 其他 batch 冲突。

# 七、时间冲突算法

## 7.1 核心判定表达式（F5，左闭右开）

资源冲突 = 下列任一集合中存在区间与请求区间重叠：

| 占用来源 | 表 | 占用状态 | 判定 |
| --- | --- | --- | --- |
| 普通预约 | `lab_instrument_reservation` | `status IN ('PENDING','FINISHED')`（未来加 `IN_USE`） | `start_time < reqEnd AND end_time > reqStart` |
| 维护时段 | `lab_instrument_maintenance` | `status = 'ACTIVE'` | 同式 |
| 冻干批次 | `lab_instrument_freeze_batch` | `status IN ('OPEN','RUNNING','FINISHED')` | 同式 |

统一判定（示例 SQL）：

```sql
-- 预约冲突计数（设备维度）
SELECT COUNT(1) FROM lab_instrument_reservation
 WHERE device_id = #{deviceId}
   AND deleted = 0
   AND status IN ('PENDING','FINISHED')   -- C3：FINISHED 为已实际使用历史，不释放
   AND start_time < #{reqEnd}
   AND end_time   > #{reqStart};
```

**占用口径（C1/C3 修订）**：

- **释放时段**：仅 `CANCELED / VOIDED`（预约取消/作废后原时段可被新预约占用）。
- **保留占用**：`PENDING`（有效预约）、`FINISHED`（已实际使用的完整历史，其历史区间不得被新正常预约重叠）；`IN_USE` 为未来签到能力预留。
- **`NO_SHOW` 已删除**（C1）：第一期无自动爽约，不参与任何判定。
- **禁止物理删除历史记录释放时间**（C3）。
- **不得**只在 Service 内存判断而不查库。

## 7.2 边界语义

- 相邻不冲突：`[09:00,10:00)` 与 `[10:00,11:00)` **不冲突**。
- 交叉即冲突：`[09:00,10:00)` 与 `[09:30,10:30)` **冲突**。
- 包含即冲突：`[09:00,12:00)` 包含 `[10:00,11:00)` **冲突**。

## 7.3 冲突返回

返回**冲突对象摘要**（占用类型、占用时段、占用单号可脱敏），前端友好提示"该时段已被占用：预约 09:30-10:30"。

# 八、并发事务处理方案

## 8.1 预约创建事务（核心）

```text
begin transaction
  1. SELECT * FROM lab_instrument_device WHERE id=? AND deleted=0 FOR UPDATE   -- 设备行锁（串行化锚点）
  2. 复核 P1-P7（权限、开放范围、时间参数）
  3. SELECT 冲突（7.1）—— reservation / maintenance / freeze_batch 各查一次
  4. 若冲突 → 抛业务异常（事务回滚）
  5. INSERT lab_instrument_reservation (status=PENDING)
  6. INSERT lab_instrument_reservation_history (action=CREATE)
 commit
```

**为何锁"设备行"而非"预约行"**：待插预约尚不存在，无法对其加锁；设备行是稳定的串行化锚点，保证同一设备的并发创建串行执行，从而 7.1 的冲突查询在锁内有效。

**辅助**：Controller/Service 入口加 `@Idempotent`（Redis 短窗口锁），防用户连点重复提交（同 lab 出入库范式）。

## 8.1.1 预约创建前的暂停校验（强制约束）

> 来源：INSTRUMENT-02 H2 正式裁决（2026-10-15）。本节为 **INSTRUMENT-03 必须继承的强制约束**，
> 不是可选建议。暂停由 INSTRUMENT-02 人工登记与人工解除（见 `04-资质信用与权限设计.md` §4），
> 预约侧的拦截在本期（INSTRUMENT-02）**尚未实现**，须在 INSTRUMENT-03 落地。

**强制约束（全部为 MUST）**：

1. **创建预约前必须检查用户是否存在生效暂停**：在 8.1 事务步骤 2「复核 P1–P7」中插入 P5 校验，
   或在提交前独立执行等价校验。
2. **ALL 范围暂停拦截该用户所有适用设备的预约**：存在 `scope_type='ALL'` 的生效暂停时，
   该用户对任意适用设备的预约创建一律拒绝。
3. **SINGLE 范围暂停仅拦截指定设备**：存在 `scope_type='SINGLE' AND device_id=目标设备` 的生效暂停时，
   拒绝该设备上的预约创建；不影响该用户其他设备的预约。
4. **校验必须在服务端执行**：判定逻辑位于 Service 层（与 8.1 设备行锁同一事务内），
   不得仅在 Controller 做形式校验后放行。
5. **不得仅依赖前端禁用按钮**：前端置灰只作体验提示，未授权的直接 API 调用必须同样被服务端拦截并返回明确业务错误。
6. **必须保证预约创建时的并发与事务一致性**：暂停校验与预约插入须处于同一事务，
   并借助 8.1 的设备行锁串行化；避免「校验通过后、插入前」期间并发创建暂停或反之产生不一致窗口。
7. **人工解除后按当前有效资质及其他预约规则重新判定**：暂停被人工解除后，该用户的预约能力
   回到既有规则（P4 资质 ACTIVE、P6 冲突、P7 其他），不得缓存"已拦截"结论。

**生效暂停的判定语义（与 INSTRUMENT-02 保持一致）**：

- 生效暂停 = `lab_instrument_suspend.status='ACTIVE'` 且 `start_time <= now`；
  **仅以 status 判定，不以 `end_time` 自动失效**——计划结束时间到达不代表自动解除（INSTRUMENT-02 H1 裁决，
  本期不启用暂停自动到期 Job）。因此预约侧不得自行用 `end_time > now` 作为"是否生效"的条件。
- 用户带生效暂停期间仍可通过资质审核（G13，H2 裁决接受）：暂停不改变资质状态判定本身，
  而是由预约侧 P5 统一拦截。故 INSTRUMENT-03 **不得**因存在暂停记录而把新审批资质强制判为 REJECTED。

**跨模块依赖**：预约模块需读取 INSTRUMENT-02 的暂停数据（`lab_instrument_suspend`）与资质数据
（`lab_instrument_qualification`），并按租户隔离校验。本期不开发预约模块。

## 8.2 预约取消事务

条件更新 + `affectedRows` 防并发（C2：用户开始前任时可取消，无提前量；开始后仅负责人/管理员）：

```sql
UPDATE lab_instrument_reservation
   SET status='CANCELED', cancel_time=NOW(), cancel_by=#{by}, cancel_reason=#{reason}
 WHERE id=#{id} AND deleted=0
   AND status = 'PENDING'                     -- 仅待使用可取消
   AND (
        (#{by}='USER'    AND user_id=#{userId} AND NOW() < start_time)  -- 本人：开始前任时可取消
     OR (#{by}='MANAGER')                                                   -- 授权负责人：开始后亦可，原因必填
     OR (#{by}='ADMIN')
       )
```

`affectedRows=0` → 明确报"状态已变更 / 无权取消 / 已过开始时间请联系负责人"。**不存在"提前 N 分钟"条件**（C2）。

## 8.3 管理员开始后调整

授权负责人/管理员可在预约开始后调整或取消（原因必填）：同一事务内**先释放原时段（置 CANCELED/VOIDED 或改时间）→ 再按 8.1 校验新时段冲突**，写入 `reservation_history(action=ADJUST, reason=必填)`。第一期无 IN_USE 态（C1），调整对象为 PENDING（含已过开始时间但尚未手工登记完成的预约）。

## 8.4 冻干批次创建

事务内锁设备行 → 7.1 三方冲突查询（batch 排除 CANCELED）→ 插入批次（`end_time = start_time + 48h`）。

## 8.5 并发保护能力边界

| 场景 | 保护手段 |
| --- | --- |
| 同时提交同一设备同一时段 | 设备行锁串行化 |
| 连点重复提交 | `@Idempotent` |
| 取消与使用并发 | 条件更新 + affectedRows |
| 管理员调整与他人预约并发 | 同 8.1 设备行锁 |

# 九、典型预约案例

## 案例 1：普通仪器（30 分钟粒度）

- 规则：`granularity_minutes=30`，`min_duration_minutes=60`，`max` 空，每天开放 08:00-22:00。
- 请求：09:00-11:30（150 分钟，30 对齐）→ 通过 P7；无冲突 → 落库。

## 案例 2：蛋白纯化仪（6h 最短，粒度待确认）

- 规则：`min_duration_minutes=360`，`granularity_minutes` **空**。
- 请求：09:00-15:00 → **P3 拦截**（粒度未配置，整机不可预约）。
- 业务确认粒度为 60 后 → 09:00-15:00（6h）通过；09:00-18:00（9h）若 60 对齐亦通过；**不存在"只能 6h/12h"限制**。

## 案例 3：酶标仪开放窗口

- 窗口：`open_days=3`（周三），`open_time=09:00-11:00`，`target_date_start/end` 由业务配置，`capacity=5`，`used_count=5`。
- 请求：某周三 09:30-10:30 → 日期命中、星期命中、时段命中，但 **capacity 已满 → P6 拒绝**。

## 案例 4：细胞膜色谱平台多设备

- 装柱机 rule：`granularity=60, min=60`；色谱设备 rule：`granularity=30, min=120`。
- 同一平台下两台设备规则不同 → 各自按自身 rule 判定（F16）。

## 案例 5：维护占用阻断

- 设备存在 `maintenance (ACTIVE, 14:00-16:00)`，用户请求 15:00-16:00 → 7.1 命中维护冲突 → 拒绝。

## 案例 6：冻干批次时段

- 冻干机已有 `batch (OPEN, T0 ~ T0+48h)`，发起人请求 `T1 ~ T1+48h` 且与前者重叠 → 7.1 命中 batch 冲突 → 拒绝（F7）。

# 十、异常场景

| 场景 | 处理 | 通知/日志 |
| --- | --- | --- |
| 预约创建时设备正被他人并发占用 | 设备行锁串行；后到者冲突查询命中 → 拒绝并提示具体占用 | 操作日志 |
| 用户到点未开始（疑似爽约） | **第一期不自动判定、不自动扣分（C1）**；保留预约记录，由授权负责人依据实际证据手工登记违规（信用流水，原因 VIOLATION） | 手工登记时写通知 + 流水 |
| 预约结束时间已过但未处理 | **第一期不按 end_time 自动 FINISHED（C1）**；时间进入过去不代表实际使用；由授权负责人核实后手工登记完成或作废 | 手工处理 + 日志 |
| 设备在预约期间故障 | 负责人可将设备置 `FAULT`；已存在预约**不自动取消**，由负责人协商改期或取消（写 history），开始后处理原因必填 | 通知相关用户 + 日志 |
| 维护时段与既有预约重叠 | 维护创建时**先做冲突校验**，与占用预约重叠则拒绝或要求先改期 | 日志 |
| 规则中途变更（粒度变大） | 仅影响**新建**预约；既有预约不变 | 操作日志 |
| 规则被停用（enabled=0） | 既有预约保留；新建一律拒绝 | 操作日志 |
| 用户资质过期但已有预约 | 已创建的 `PENDING` 保留；**新建**被 P4 拦截 | 通知 + 日志 |
| 时间跨天且粒度无法对齐 | 拒绝，提示选择合法边界 | — |
| 冻干运行中设备故障 | 负责人可取消/结束批次（需原因，见 05） | 通知参与者 + 日志 |
| 管理员调整与用户取消并发 | 8.2/8.3 条件更新 + affectedRows，失败方报明确原因 | 日志 |
