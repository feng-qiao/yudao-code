# 一、设计目标

1. 设计仪器使用**资质申请与审核**流程，并区分"审批历史"与"当前有效资质"。
2. 设计**统一信用账户**（初始 100，允许超过 100），首次审核通过**最多初始化一次**，其后审核其他仪器不重复初始化。
3. 设计**加扣分流水**（不可随意删除）与**人工暂停**机制。
4. 建立**权限矩阵**，所有限制**后端鉴权**（F18）。

# 二、资质审批设计

## 2.1 流程

```text
普通用户
   │
   ├─ 查看仪器使用须知（notice，可选要求确认）
   │
   ▼
提交资质申请（**target 固定为 DEVICE，第一期仅设备级资质，C4**）
   │  校验：无同设备的 PENDING；未持有同设备的 ACTIVE 资质；通过平台内一台设备不赋予其他设备资格
   ▼
PENDING 待审核
   │
   ├─ 仪器负责人审核 ─┬─ 通过 → APPROVED
   │                  └─ 驳回（必填意见）→ REJECTED
   │
   └─ 申请人撤回 → CANCELED
                    │
                    ▼
             APPROVED → 生成/激活 QUALIFICATION(ACTIVE)
                    │        └─ 同一事务内尝试初始化信用账户（最多一次，F2）
                    ▼
             REJECTED → 申请人修改后重新提交（新增申请单，保留历史）
```

## 2.2 审批历史 vs 当前资质

| 概念 | 表 | 说明 |
| --- | --- | --- |
| 审批历史（时间线） | `lab_instrument_qualification_apply_history` | 每次 SUBMIT/APPROVE/REJECT/CANCEL/RESUBMIT 记一行，只增不改 |
| 当前有效资质 | `lab_instrument_qualification` | `status=ACTIVE` 为权威来源；撤销/过期保留行 |

**必须区分**：列表页展示"当前是否有效"读 qualification；审计/追溯读 apply + history。

## 2.3 资质状态机（复用 00 文档 4.3）

```text
ACTIVE ──到期──► EXPIRED      （系统 Job）
ACTIVE ──有暂停记录──► SUSPENDED （负责人）
SUSPENDED ──暂停解除──► ACTIVE   （负责人）
任意 ──严重违规──► REVOKED      （管理员）
EXPIRED / REVOKED ──► 必须重新申请（不得直接复活）
```

## 2.4 并发与幂等（F2）

- 同一 (tenant, device_id, applicant) 只允许**一条 PENDING**：Service 校验 + Redisson 锁 `instrument:qual:{tenant}:device:{deviceId}:{user}`。
- 审核通过时：
  1. 事务内锁定 apply 行（`FOR UPDATE`）；
  2. 条件更新 `PENDING → APPROVED`（`affectedRows` 校验，防重复审核）；
  3. 创建/激活 qualification；
  4. **尝试**初始化信用账户（见 3.3）；
  5. 写 apply_history。
- 重复审核（并发）由 2 条件更新拦下，`affectedRows=0` → 报"状态已变更"。

# 三、统一信用账户设计

## 3.1 基本原则

| 规则 | 说明 |
| --- | --- |
| 初始 100 分 | `credit_account.score` 默认 100 |
| **允许超过 100** | **不得设最高分约束 / CHECK / 业务上限**（F1） |
| 每租户每用户唯一 | `UNIQUE(tenant_id, user_id)` |
| 首次初始化仅一次 | `initialized` 标记 + 唯一键 + 锁（F2） |
| 后续审核不重复初始化 | 已存在账户 → 直接跳过（F3） |
| 加扣分必留流水 | `credit_flow`，无删改接口（F4） |
| 低于 80 分自动禁用 | **暂不启用（F10）**，仅预留 |

## 3.2 何时创建账户

**唯一触发点**：用户**首次**通过任意仪器资质审核时。

- 若账户不存在 → 创建（`score=100, initialized=1`）。
- 若账户已存在 → **不创建、不重置、不加分**（无论审核多少台仪器）。

## 3.3 并发不重复赠送 100 分（F2 核心）

三层保护：

| 层 | 手段 | 效果 |
| --- | --- | --- |
| 1 | DB 唯一键 `uk_account_tenant_user (tenant_id, user_id)` | 并发插入只有一个成功，其余唯一键冲突 |
| 2 | Redisson 锁 `instrument:credit:account:{tenant}:{user}` | 锁内"查不到才插入" |
| 3 | 与资质审核同一事务 | 审核回滚则账户初始化一并回滚，保证"审核结果与初始化一致" |

**"资质审核结果与信用账户初始化一致"**：二者同一事务，要么都成功，要么都回滚。

## 3.4 信用事务方案（加/扣分）

```text
begin transaction
  1. SELECT * FROM lab_instrument_credit_account WHERE id=? FOR UPDATE   -- 锁账户行
  2. scoreBefore = account.score
  3. scoreAfter  = scoreBefore + delta     -- delta 可正（加）可负（扣）
  4. UPDATE credit_account SET score=scoreAfter, last_change_time=NOW()
  5. INSERT credit_flow (change_type, score_change=delta, score_before, score_after,
                         reason_type, biz_type, biz_id, reason, operator, operate_time)
 commit
```

- **同时调整**：行锁保证串行，无丢失更新。
- **重复提交防护**：入口 `@Idempotent`；同一 biz（如负责人对同一预约违规登记）扣分通过业务唯一性防重复（Service 校验"该 biz 是否已产生同类型流水"）。
- **审计**：流水记录 before/after、原因、操作人、时间，不提供删除/修改。

## 3.5 加扣分来源（设计清单，规则值待业务确认）

| 业务 | 方向 | 触发 | 说明 |
| --- | --- | --- | --- |
| 预约/使用违规 | 扣 | **授权负责人手工登记** | 必须有实际证据与原因；**第一期无自动爽约判定（C1）** |
| 预约逾期未归还/未结束（若适用） | 扣 | 负责人手工登记 | 待确认；**不做系统自动判定（C1）** |
| 冻干批次违规 | 扣 | 负责人登记 | 关联违规事件 |
| 用户取消预约 | — | — | **开始前任时可取消（C2），不扣分、无提前量限制** |
| 奖励（如遵守规范、协助维护） | 加 | 负责人手工登记 | **必须业务依据**，非自动 |
| 人工调整 | 加/扣 | 授权人 | 必填原因 |
| 提交报修 | — | — | **不自动加分（F12）** |
| 维修完成奖励 | 加 | 负责人 | 设计**预留关联**，不得自动触发 |

> **C1 强调**：第一期不存在系统 Job 自动置 `NO_SHOW`/自动扣分；时间进入过去不等于实际使用。所有扣分均由授权负责人凭证据手工登记。
> **F12 强调**：报修**不自动加分**；加分仅由负责人按业务依据手工登记或经确认的规则触发。

## 3.6 低于 80 分自动禁用（暂不启用）

- 设计中**不实现**触发逻辑，仅在 `04` 预留说明与接口位置。
- 若要启用，须业务确认"阈值、触发动作（禁预约 / 暂停 / 仅提醒）、恢复条件"，并作为独立子任务。

# 四、人工暂停设计

## 4.1 维度与时长（F9）

| 项 | 取值 |
| --- | --- |
| 维度 | SINGLE 单仪器（指定 device_id） / ALL 全仪器 |
| 时长 | 1 / 3 / 7 / 14 / 30 天；或**自定义截止日期** |
| 解除 | 支持**提前解除**（附原因） |
| 记录 | 原因、操作人、操作时间、解除人、解除时间、解除原因 |
| 历史 | 全部保留（不物理删除） |

## 4.2 暂停状态机

```text
(新建) → ACTIVE ──提前解除──► RELEASED
              └──到期（Job）──► EXPIRED
```

## 4.3 暂停生效判定（预约时）

用户发起预约时，检查是否存在：

```sql
SELECT COUNT(1) FROM lab_instrument_suspend
 WHERE user_id=#{uid} AND deleted=0 AND status='ACTIVE'
   AND start_time <= NOW() AND end_time > NOW()
   AND (scope_type='ALL' OR (scope_type='SINGLE' AND device_id=#{deviceId}));
```

命中 → 拒绝预约（03 文档 P5）。

## 4.4 暂停与资质关系

- 暂停是**用户级**（不改变资质状态）还是**资质级**（联动 `qualification=SUSPENDED`）？
- 建议：暂停记录生效期间，对应 `qualification` 置 `SUSPENDED`；解除后恢复 `ACTIVE`（00 文档 4.3 已定义该联动）。
- 标记**待确认 G12**：暂停是否强制联动资质状态，或两者独立。

## 4.5 自动到期 Job

`@TenantJob` 扫描 `status='ACTIVE' AND end_time <= NOW()` → 置 `EXPIRED`，并恢复关联资质（如采用联动方案）。

# 五、角色与权限矩阵

## 5.1 角色定义（沿用现有系统机制）

| 角色 | 来源 | 说明 |
| --- | --- | --- |
| 平台超级管理员 | 现有系统机制（`*:*:*` 通配） | 全部权限 |
| 本草基因管理员 | 现有/新建业务管理角色 | 仪器全局业务管理 |
| 仪器负责人（DEVICE） | `manager.scope=DEVICE` | 只管自己负责设备 |
| 平台负责人（PLATFORM） | `manager.scope=PLATFORM` | 管平台内设备 |
| 实验室维修负责人（ROOM_REPAIR） | `manager.scope=ROOM_REPAIR` | 处理本房间工单 |
| 普通用户 | 现有（如 role 904） | 仅管理自己的申请/预约/工单 |

> 仪器负责人/维修负责人**不是系统角色**，而是**业务关系**（`manager` 表）；权限判定 = 系统角色（能否进入功能） + 业务关系（数据范围）。**不得**用角色代替负责人关系（F19）。

## 5.3 后端鉴权要求（F18，强制）

| 校验点 | 后端实现 |
| --- | --- |
| 功能准入 | `@PreAuthorize("@ss.hasPermission('lab:instrument:xxx:yyy')")` |
| 数据范围（负责人） | Service 层**显式**校验：`manager` 表中是否存在 (scope, target_id, currentUser, ACTIVE)；不存在 → 拒绝 |
| 本人数据 | Service 校验 `user_id == 当前登录用户` |
| 管理端列表 | `@DataPermission`（部门维度）+ 业务范围二次过滤 |
| 信用/暂停授权范围 | Service 校验操作人是否对目标设备/用户有授权 |
| 前端按钮 | `v-hasPermi` **仅辅助显示**，不作为安全边界 |

> **不得仅依赖前端隐藏按钮**（F18）。所有越权路径必须有后端拦截与明确错误码。

## 5.4 数据范围判定伪代码

```text
function canManageDevice(currentUser, deviceId):
    if isSuperAdmin(currentUser) or isLabAdmin(currentUser): return true
    return existsManager(scope=DEVICE, target_id=deviceId, userId=currentUser, status=ACTIVE)
        or existsManager(scope=PLATFORM, target_id=device.platformId, userId=currentUser, status=ACTIVE)

function canHandleRepair(currentUser, roomId, deviceId):
    if isSuperAdmin or isLabAdmin: return true
    if existsManager(scope=DEVICE, target_id=deviceId, user=currentUser, ACTIVE): return true
    if existsManager(scope=ROOM_REPAIR, target_id=roomId, user=currentUser, ACTIVE): return true
    return false
```

# 六、审计规则

| 业务动作 | 审计载体 |
| --- | --- |
| 资质申请/审核 | `qualification_apply_history` + `@OperateLog` |
| 信用加扣分 | `credit_flow`（含 before/after/reason/operator）+ `@OperateLog` |
| 暂停创建/解除 | `suspend`（含 release_*）+ `@OperateLog` |
| 预约创建/取消/调整 | `reservation_history` + `@OperateLog` |
| 冻干批次创建/取消/补录 | `freeze_participant`（补录字段）+ `@OperateLog`（见 05） |
| 工单分配/受理/转交/完成 | `repair_history` + `@OperateLog` |
| 规则/负责人/设备配置 | `@OperateLog` |

**审计不可替代**：`@OperateLog` 记录接口调用，业务历史表记录业务语义（原因、前后状态）。

# 七、异常与边界

| 场景 | 处理 |
| --- | --- |
| 审核人无该设备权限 | 后端拒绝（5.3） |
| 审核时申请人信用被暂停 | 按业务规则：建议**允许资质通过但不影响暂停**，或**拒绝**（待确认 G13） |
| 账户已存在但 `initialized=0`（异常数据） | 视为未初始化，允许初始化一次；记日志 |
| 重复提交审核 | 条件更新 affectedRows=0 → 报错 |
| 暂停无依据 | 拒绝（原因必填） |
| 负责人账号停用 | 见 06 文档（工单转待分配） |
| 提前解除暂停 | 记录 release_reason + 操作人 |
| 信用分数为负 | **允许**（不加下界约束，仅业务展示）；是否封底待确认 G14 |
