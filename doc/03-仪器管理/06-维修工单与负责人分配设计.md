# 一、设计目标

建立**科研仪器报修与通用仪器报修的统一工单体系**：

1. 统一的报修资料模型。
2. **自动分配**：设备专属维修负责人 → 实验室维修负责人 → 管理员待分配（F11）。
3. 完整工单处理流：提交/分配/受理/处理/转交/完成/关闭/查询历史。
4. 处置负责人**未配置/离职/停用/多人/转交**等边界。
5. 与信用奖励**关联但不自动加分**（F12）。

# 二、报修资料模型（`lab_instrument_repair_order`）

| 资料 | 字段 | 必填 | 说明 |
| --- | --- | --- | --- |
| 报修人 | `reporter_user_id` / `reporter_name` | 是 | 系统取当前登录用户 + 姓名快照 |
| 报修实验室 | `room_id` | 否 | 关联 `lab_instrument_room.id` |
| 报修设备 | `device_id` / `device_name` | 否 | 科研仪器通常有 device；通用仪器可无设备（走资产编号） |
| 资产编号 | `asset_no` | 否 | 设备资产编号 |
| 故障描述 | `fault_desc` | **是** | 文字描述 |
| 铭牌图片 | `nameplate_file_id` / `nameplate_file_name` | 否 | `infra_file.id` + 快照 |
| 故障图片 | `fault_file_id` / `fault_file_name` | 否 | `infra_file.id` + 快照 |
| 联系方式 | `contact_mobile` | 否 | 默认取 `system_users.mobile` |
| 维修口径 | `repair_scope` | 是 | SCIENCE 科研仪器 / GENERAL 通用仪器 |
| 处理进度 | `status` + 处理人/时间字段 | 是 | 见第三章 |

> **统一性**：科研仪器与通用仪器**共用同一张表与同一套接口**，仅以 `repair_scope` 区分口径；分页/统计可按该字段筛选。

# 三、工单状态机（复用 00 文档 4.7）

状态集：`SUBMITTED` / `ASSIGNED` / `ACCEPTED` / `PROCESSING` / `TRANSFERRED` / `FINISHED` / `CLOSED`

| 转换 | 执行人 | 前置条件 | 失败处理 | 通知/日志 |
| --- | --- | --- | --- | --- |
| (新建) → SUBMITTED | 报修人 | 必填资料齐全 | 缺项拒绝 | 日志 |
| SUBMITTED → ASSIGNED | 系统 | 路由命中负责人（F11） | **未命中 → 待分配（不自动分配）** | 通知处理人 + 日志 |
| ASSIGNED → ACCEPTED | 处理人 | — | — | 通知报修人 + 日志 |
| ACCEPTED → PROCESSING | 处理人 | — | — | 日志 |
| PROCESSING → FINISHED | 处理人 | 填写处理结果 | — | 通知 + 日志 |
| ACCEPTED/PROCESSING → TRANSFERRED → ASSIGNED | 处理人 | 指定新处理人（需原因） | — | 通知双方 + 日志 |
| FINISHED → CLOSED | 报修人/管理员 | 验收 | — | 日志 |
| 任意非终态 → CLOSED | 管理员 | 无效工单（需原因） | — | 日志 |

# 四、自动分配设计（F11）

## 4.1 路由优先级

```text
提交工单
   │
   ├─ P1 设备专属维修负责人
   │     EXISTS manager(scope=DEVICE, target_id=device_id, status=ACTIVE)
   │     → handler = 该负责人, handler_source = DEVICE_MANAGER
   │
   ├─ P2 实验室维修负责人
   │     EXISTS manager(scope=ROOM_REPAIR, target_id=room_id, status=ACTIVE)
   │     → handler = 该负责人, handler_source = ROOM_MANAGER
   │
   └─ P3 未命中 → status 保持 SUBMITTED（待分配状态）
         → 通知管理员"有待分配工单", handler_source = 空
```

## 4.2 与现有系统关系

| 检查项 | 结论 |
| --- | --- |
| 是否复用 `system_dept` 负责人 | **否**。`system_dept.leader_user_id` 是组织架构负责人，与"实验室维修负责人"语义不同（01 报告 K10） |
| 负责人存储 | 必须落到正式业务关系表 `lab_instrument_manager`（F19），**不得用字典配置存用户 ID** |
| 设备/房间关系 | 由 `device.room_id` + `manager` 表共同确定 |

## 4.3 一个房间多个管理人员

- `manager(scope=ROOM_REPAIR)` 允许同一 `target_id(room)` 存在**多条 ACTIVE**（即多负责人）。
- **G26 已于 2026-10-15 正式裁决为方案 A**：同一实验室允许配置多名有效维修负责人；
  不得限制单 ACTIVE、不得因新增自动解除既有负责人、同一用户同实验室同类型不得重复、
  解除单人不影响其他人、不引入主/协同负责人等级（裁决记录见 11-修订记录 §R3）。
- 工单分配规则（多名负责人如何接收/受理工单）**留待 INSTRUMENT-06 确定**：
  当前不得实现自动轮询、随机分配、默认分配给第一名、自动平均分配或未经确认的抢单规则；
  数据模型层"多 ACTIVE"已按裁决 A 落地。
- 表结构支持多负责人：`idx_scope_target(scope, target_id, status)` 可查全部 ACTIVE。

## 4.4 负责人尚未配置

- P1、P2 均未命中 → 工单 `SUBMITTED`（待分配），通知管理员。
- 管理端"待分配工单"列表可见并手工分配。

## 4.5 负责人离职或账号停用

- 分配前校验处理人 `system_users.status == 0`（启用）。
- 若命中的负责人**已停用** → 视为**未命中**，降级到下一级路由；全部未命中 → 待分配。
- 若工单已分配给某人而该人后续停用 → 允许**转交**（第六章）或管理员重新分配。

## 4.6 工单转交

- 当前处理人可将工单转交指定新处理人：`TRANSFERRED → ASSIGNED`。
- 必须记录：`from_handler_id`、`to_handler_id`、原因、操作人、时间（写 `repair_history`）。
- 新处理人须为启用用户，且（建议）属于该设备/房间授权范围（待确认 G27）。

## 4.7 历史负责人追溯

- `repair_history` 逐条记录每次 ASSIGN/TRANSFER 的 from/to handler，可完整重建"谁在何时处理"。
- `manager` 表保留负责人变更历史（`effective_from/to`），可追溯"当时谁是负责人"。

# 五、工单处理流程

```text
报修人提交（SUBMITTED）
   │  自动路由（4.1）
   ├─ 命中 → ASSIGNED → 处理人受理（ACCEPTED）→ 处理（PROCESSING）→ 完成（FINISHED）
   │         └─ 可转交（TRANSFERRED → ASSIGNED）
   └─ 未命中 → SUBMITTED（待分配）→ 管理员手工分配 → ASSIGNED → …
                                          │
                                          ▼
                                     报修人验收 → CLOSED
```

各步骤均写 `repair_history` + `@OperateLog`；受理/完成/关闭均通知报修人与处理人。

# 六、与信用奖励的关联（F12）

| 规则 | 说明 |
| --- | --- |
| 提交报修 | **不自动加分**（F12 强制） |
| 维修完成奖励 | **设计预留**：可关联 `credit_flow`（`biz_type=REPAIR, biz_id=order.id`），但**不自动触发**；由负责人按依据手工登记 |
| 加分授权 | `canManageDevice`/`canHandleRepair` 授权范围内的负责人方可登记 |
| 分值 | **待确认 G17**（建议小额，如 +1~+2） |
| 报修频次异常 | 可扩展为违规识别（**不自动扣分**），标记待确认 |

> 不得把"提交报修"与加分绑定；加分须有业务依据与操作人。

# 七、权限与数据范围

| 操作 | 权限判定 |
| --- | --- |
| 提交报修 | 任意登录用户 |
| 查看自己工单 | `reporter_user_id == 当前用户` |
| 处理工单 | `canHandleRepair(currentUser, roomId, deviceId)`（04 文档 5.4）或被分配 |
| 转交 | 当前处理人 + 授权范围校验 |
| 管理员分配/关闭 | `lab:instrument:repair:manage` 权限 |
| 后端鉴权 | `@PreAuthorize` + Service 校验（F18） |

# 八、异常场景

| 场景 | 处理 |
| --- | --- |
| 未配置任何负责人 | 进入待分配，通知管理员 |
| 命中负责人已停用 | 降级路由；全未命中 → 待分配 |
| 一房间多负责人 | 多 ACTIVE 已裁决（G26=A）；工单分配规则待 INSTRUMENT-06 |
| 转交给无权限用户 | 拒绝（G27） |
| 处理人长期不受理 | 可扩展超时提醒/自动升级（**待确认 G28**，本阶段不实现） |
| 设备已报废但报修 | 允许提交，处理人可将工单关闭（无效工单） |
| 同一设备短时间内重复报修 | 允许；可关联为重复工单（**待确认 G29**） |
| 工单完成后设备未恢复 | 处理人须同步将 device 状态由 FAULT 改回 NORMAL/MAINTENANCE（联动） |
