# INSTRUMENT-06 SQL 58/59 正式部署执行与验收手册

**用途**：供负责人、DBA 与业务验收人员进行部署前准备和获批后的操作。  
**当前状态**：SQL 58/59 **未执行**；目标库状态 **UNKNOWN**；本手册不构成数据库写入授权。  
**配套文件**：[INSTRUMENT-06-SQL58-59目标库只读预检.sql](INSTRUMENT-06-SQL58-59目标库只读预检.sql)  
**依据**：最新无签到业务裁决、R4 69 号报告、SQL 58 与 SQL 59 设计稿。

## 1. 操作边界

1. 先用只读账号连接目标 `labplatform`，运行配套 SELECT-only 文件；不要在正式库试跑写入脚本。
2. 记录 MySQL 版本、目标 schema、五表字段/索引、菜单 ID、权限码、角色、套餐与租户的结果。任何结果与设计值不同、查询失败或无法解释时停止。
3. SQL 58 是 DDL、SQL 59 是菜单/角色/套餐 DML。两者不得被视作一个整体事务：MySQL DDL 可能隐式提交。
4. SQL 59 §8.2.1 自动套餐 JSON 回退表达式存在语义问题，**禁止使用该回退段**。遇到失败应停止并由 DBA 依据独立备份制定恢复步骤。
5. SQL 58/59 的实际执行必须等待负责人在复核只读结果后另行明确授权。SQL 58/59 当前均未执行。

## 2. SQL 58 执行前检查

- 确认 `DATABASE()` 是预期的 `labplatform`，记录 MySQL 版本。
- 查询五张表：`lab_instrument_fault_report`、`lab_instrument_repair_order`、`lab_instrument_repair_history`、`lab_instrument_device_status_history`、`lab_instrument_reservation_impact`。
- 若五张都不存在：确认 SQL 58 前置设备、设备负责人、预约表均存在，并检查 DDL 与当前代码版本一致。
- 若部分表已存在：**停止**。对每张现存表逐字段、逐索引、唯一键、类型、默认值、字符集进行 schema diff；另编单独迁移方案，不能依赖 `CREATE TABLE IF NOT EXISTS`。
- 核对影响表唯一约束为 `(tenant_id, impact_key)`，列长度/字符集/排序规则与代码生成值兼容。
- 核对是否有同名对象、残留旧表、已有维修业务数据及备份恢复能力。
- 备份目标 schema 的 DDL；确认可恢复的完整数据库备份，以及备份校验记录。备份文件位置由 DBA 管理，不在工作区落放凭据。

## 3. SQL 58 执行步骤（获批后）

1. 由 DBA 在维护窗口确认目标库、备份完成、应用写入安排和授权单号。
2. 不使用“全部 SQL 一次性事务回滚”的表述。按 SQL 58 建表顺序逐表执行，并在每张表完成后检查命令结果与 `information_schema` 字段/索引。
3. 任一语句失败、执行目标错误、列/索引与设计不符：停止后续 DDL，记录已完成的表；不要盲目 DROP 或重放脚本。评估前向修复或从备份恢复。
4. 不将 SQL 59 插入 SQL 58 执行窗口中的 DDL 批次；五表核对完成后再进入 SQL 59 阶段。

## 4. SQL 58 执行后验证

- 五张表均存在且 engine 为 InnoDB。
- DO 对应的每个列名/类型/可空性/默认值与 SQL 58 一致。
- 检查主键及索引；重点检查 `uk_tenant_impact_key(tenant_id, impact_key)`。
- 检查五表租户列、软删除列、审计列齐备。
- 仅当 schema 核验全通过、无错误记录后进入菜单授权阶段。不得向表写入测试数据。

## 5. SQL 59 执行前检查

先执行配套查询，并逐项满足：

- 菜单 ID 13684–13688 未被任何有效或软删除行占用；权限码无冲突。
- 父菜单 13600、祖先目录 13478 存在、租户归属与启用状态符合目标；sort 值没有冲突。
- 角色 904 普通用户、906 本草基因管理员、908 设备负责人、909 维修负责人真实状态及 tenant_id 均已核对；角色 909 的 ID 与 `instrument_repair_manager` code 同时空闲。
- 租户 162 与套餐 114 存在且状态可用；`menu_ids` 为有效 JSON，且尚未意外包含本批 ID。
- 预留执行前快照：目标菜单行、角色行、角色菜单关联、套餐 `menu_ids` 原始完整 JSON、当前索引/约束和执行前授权数量。
- 确认各受影响表均为事务型存储引擎，并计划在同一连接执行 SQL 59 DML。若不能证明或工具会自动分段提交，停止并先修订执行脚本。
- 如果 ID 已占用、菜单状态/层级不符、套餐 JSON 无效或角色归属异常，停止。禁止自动换 ID 或擅自改套餐。

## 6. SQL 59 执行步骤（获批后）

1. 负责人确认只读预检结果、备份及 SQL 59 评审版本，并单独提供执行授权。
2. 先备份 `system_menu`、`system_role`、`system_role_menu` 中目标范围及 `system_tenant_package` 的套餐 114 原始行。原始套餐 JSON 应以可恢复备份/审计记录完整保存。
3. 在确认事务表与客户端行为后，按一个事务执行 SQL 59 的角色创建、菜单创建、套餐追加、角色菜单授权和 SELECT 验收。事务中任何验收不通过都回滚该 DML 事务并停止；不要继续到缓存刷新。
4. SQL 58 DDL不参与上述事务；如果 SQL 59 的客户端不能保证单事务，应停止并由 DBA 拆分出经过评审的脚本，不要按原注释盲目 `source` 多份脚本。
5. SQL 59 本次静态复核发现 §8.2.1 JSON 回退语句不可靠。发生错误时保留现场与错误文本，不运行该段，也不要手工执行 DELETE；由负责人/DBA 用已备份快照制定恢复步骤。

## 7. SQL 59 执行后验证

- 角色 909 唯一存在且租户为 162、状态正确；角色名称和 code 符合冻结设计。
- 13684–13688 五条菜单各自权限码、类型、层级、sort、path、component、租户、状态正确；component 为 `lab/instrument/repair-order/list`。
- 套餐 114 的原有 JSON 全部保留，并只增加预期的 13684–13688；`JSON_VALID=1`。
- 角色矩阵与 SQL 59 一致：904 仅页面/提交；906 获得管理所需全部菜单；908 不得自动获得维修菜单；909 获祖先链、页面、submit、handle，不得获得 admin。
- 查询跨租户残留授权和菜单软删除 ID；不符合预期即停止、留证。
- 不自动分配 `system_user_role`。维修负责人账号需先由业务确认 ROOM_REPAIR 关系，再按组织的用户角色流程人工指派。

## 8. 停止条件

- 当前 schema、MySQL 版本、表结构或唯一键与预期不一致。
- 任一固定 ID、权限码、组件路径、角色 code、套餐或租户存在冲突。
- SQL 语句失败、affected rows 与预期不符、套餐 JSON 意外变化或验收查询不通过。
- 无法确认事务表、自动提交行为、备份恢复可用性或执行人授权。
- 执行窗口内出现不相关数据库变更或其他操作者写入目标表。

停止后保留完整查询结果、执行记录及错误文本，不继续缓存刷新或用户验收。不得擅自改 ID、覆盖现有行、清除缓存或重试写入。

## 9. 备份与恢复

- DDL：MySQL DDL 可能隐式提交，不能依赖 `ROLLBACK` 撤销已建表。优先依据备份恢复；若数据库中已产生有效业务数据，禁止 DROP 表，应由 DBA 设计前向修复或数据迁移。
- DML：只在确认 InnoDB、单连接事务和客户端无自动提交后，才可在授权的执行流程中使用事务回滚未提交修改。
- 已提交 SQL 59 的恢复：使用执行前保存的原始菜单/角色/关联/套餐快照，由 DBA 生成审阅过的恢复脚本。不要使用 SQL 59 §8.2.1 自动更新套餐 JSON；其表达式不可靠，且对现有菜单顺序/长度有潜在影响。
- 回滚前应确认是否已有人操作菜单、指派角色或产生维修数据；回滚方案应避免删除其他批次或人工新增的数据。

## 10. 菜单缓存刷新

SQL 59 直接写数据库不会触发应用层缓存清理。数据库验收通过后，按项目批准的应用界面流程刷新菜单/角色缓存；SQL 59 草稿建议由菜单管理界面保存触发全局菜单缓存失效，再分别保存目标角色菜单触发角色缓存失效。不得使用 Redis 命令或未经批准的脚本直接改缓存。

刷新后让测试用户退出并重新登录，验证左侧菜单和按钮权限。缓存步骤需留存操作人、时间和截图/审计证据。若菜单未出现或按钮越权，不要扩大角色授权，先排查权限数据和缓存。
