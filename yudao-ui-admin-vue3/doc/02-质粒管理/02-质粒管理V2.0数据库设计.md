# 一、数据库设计目标

V2.0数据库不再采用：

```text
lab_plasmid
    +
lab_plasmid_ext
```

简单扩展的方式。

改为按照业务领域拆分：

```text
质粒类型
    ↓
质粒档案
    ├── 保存/存储信息
    ├── 审核历史
    ├── 当前库存
    │      └── 库存流水
    └── 借用
           └── 归还

用户
    ├── 违规
    └── 黑名单
```

设计原则：

1. 一个业务对象一个明确职责。
2. 动态库存独立于质粒基础档案。
3. 库存变化必须保留流水。
4. 审核必须保留历史。
5. 借用与归还独立管理。
6. 违规与黑名单独立管理。
7. 审核状态与库存状态分离。
8. 优先复用 RuoYi-Vue-Pro 框架字段和能力。
9. 不删除现有数据表，先完成V2.0迁移设计。
10. 不允许AI自行修改本数据库设计。

# 六、删除/废弃字段

原 `lab_plasmid` 中：

```text
build_date
type_remark
status
```

不再按原含义使用。

其中：

### `build_date`

当前V2.0需求没有明确要求独立的“构建日期”。

因此暂不纳入核心字段。

### `type_remark`

明确删除。

### `status`

明确废弃原：

```text
0 可用
1 低库存
2 耗尽
3 停用
```

改为：

```text
audit_status
```

以及库存表中的：

```text
inventory_status
```

------

# 七、plasmid_no唯一性

`plasmid_no`必须唯一。

推荐数据库约束：

```text
UNIQUE(plasmid_no, tenant_id)
```

同时需要后端在新增和修改时进行业务校验。

# 八、seq_no设计

`seq_no`由系统生成。

用户不能输入或修改。

具体生成策略：

> 在后端 Service 层统一实现。

不能由前端生成。

V2.0数据库设计阶段暂不规定具体算法。

# 九、audit_status

推荐：

```text
DRAFT
PENDING
APPROVED
REJECTED
DISABLED
```

含义：

| 值         | 含义     |
| ---------- | -------- |
| `DRAFT`    | 草稿     |
| `PENDING`  | 待审核   |
| `APPROVED` | 审核通过 |
| `REJECTED` | 审核驳回 |
| `DISABLED` | 停用     |

数据库可以使用 `varchar(30)`。

这样未来增加状态时比 tinyint 更容易维护和阅读。

最终编码规范以项目既有字典/枚举风格为准。

# 十四、动态库存与volume

`lab_plasmid_storage.volume`可以作为：

> 质粒档案/保存信息中的业务静态或辅助信息。

但是：

> **不能作为动态库存唯一来源。**

动态库存必须使用：

```text

```

以及：

```text

```

进行管理。

这是V2.0数据库最重要的边界之一。

# 二十一、库存流水类型

支持：

```text
INBOUND       入库
OUTBOUND      出库
BORROW        借用
RETURN        归还
ADJUSTMENT    盘点调整
DISPOSAL      报废/处置
```

------

# 二十二、库存流水数量规则

为了避免正负号混乱：

建议：

```text
quantity
```

统一保存：

> 本次业务实际变化量的绝对值。

通过：

```text
flow_type
```

判断增加或减少。

例如：

```text
入库 100
借用 20
归还 10
```

而不是：

```text
+100
-20
+10
```

最终计算由业务类型决定。

这样更容易避免前端传入错误的负数。

------

# 二十三、库存事务要求

库存变化必须：

```text
锁定库存记录
↓
读取当前库存
↓
计算新库存
↓
更新库存
↓
写入库存流水
↓
提交事务
```

必须避免并发情况下：

```text
库存被重复扣减
```

后端需要使用事务和适当的行锁/乐观并发控制。

具体实现方式由后端按照项目规范确定。

# 三十六、为什么 storage 独立

`lab_plasmid`保存：

> “这个质粒是什么”。

`lab_plasmid_storage`保存：

> “这个质粒怎么保存”。

这样可以避免基础档案表越来越臃肿。

------

# 三十七、为什么 audit 独立

审核是历史过程。

例如：

```text
第一次提交 → 驳回
第二次提交 → 驳回
第三次提交 → 通过
```

如果只在 `lab_plasmid` 中保存：

```text
audit_status
reviewer
review_time
```

历史会被覆盖。

所以必须：

```text
lab_plasmid
+
lab_plasmid_audit
```

------

# 三十八、为什么 inventory 独立

库存是动态变化数据。

如果直接：

```text
lab_plasmid.volume = 800
```

无法回答：

```text
为什么变成800？
谁扣的？
什么时候扣的？
扣了多少？
因为哪次借用？
```

因此：

```text
inventory
+
inventory_flow
```

必须分离。

------

# 三十九、为什么 borrow 和 return 独立

借用和归还是两个不同业务动作。

例如：

```text
借用300
第一次归还100
第二次归还100
第三次归还100
```

所以：

```text
borrow 1:N return
```

比把归还信息全部塞进借用表更加合理。
